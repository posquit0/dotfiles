# HTML 원페이지 리포트 표준 가이드

전달받은 내용을 **단일 HTML 파일** 리포트로 만든다. 독자는 위에서 아래로 스크롤하며 읽고, 왼쪽 목차로 섹션을 오간다.
디자인·동작 표준은 `templates/report.html`에 고정되어 있고, 리포트마다 바뀌는 것은 **콘텐츠와 accent 색 네 값뿐**이다.

요청: $ARGUMENTS
(치환되지 않았으면 대화에서 주제와 자료를 파악한다. 무엇에 대한 리포트인지 알 수 없으면 묻는다)

## 0. 절대 규칙

- 파일 하나로 완결. 외부 리소스는 **아래 두 가지만** 허용하며, 템플릿에 이미 들어 있으므로 추가·변경하지 않는다.
  그 외 외부 CSS/JS/이미지 로드 금지 (그림은 mermaid 또는 인라인 SVG)
  - Google Fonts 링크 (IBM Plex Sans KR · JetBrains Mono) — 오프라인이면 시스템 폰트로 자연 강등
  - mermaid ESM (`cdn.jsdelivr.net`, 버전 고정) — 문서에 `pre.mermaid`가 있을 때만 동적으로 불러온다
- 언어는 한국어 (`<html lang="ko">`)
- **`<head>`의 생성 표식 메타 2줄은 반드시 그대로 남긴다** (리포트 탐색·일괄 마이그레이션 기준):
  ```html
  <meta name="generator" content="html:report">
  <meta name="html-report-version" content="2026-10-26">
  ```
  `html-report-version`은 리포트를 만들 때 쓴 **템플릿 버전**이며 포맷은 `YYYY-MM-DD`로 고정한다.
  내용만 바꿀 때는 건드리지 않고, 템플릿 구조가 바뀌어 리포트를 그 버전으로 옮겼을 때만 갱신한다.
  생성된 리포트 찾기: `grep -rl html-report-version --include='*.html' .`
- 템플릿의 구조 CSS·JS(목차·스크롤스파이·탭·스위치·mermaid 로더·인쇄)는 수정하지 않는다.
  커스터마이징은 `:root` 첫 줄의 accent 네 값(`--accent-l` `--accent-soft-l` `--accent-d` `--accent-soft-d`) 교체만
- **`nav.toc`는 비워 둔다** — JS가 `section.lv2[id] > h2`를 읽어 채운다. 목차 링크를 손으로 쓰지 않는다
- **모든 h2는 `<section id="…" class="lv2">` 안에 둔다.** id는 ASCII 소문자·하이픈(`source-dag`), 문서 안에서 유일.
  목차·딥링크(`파일#id`)·publish-html 섹션 링크가 모두 이 id를 쓴다. 딥링크를 걸 만한 h3에도 id를 준다
- 인라인 style로 font-size를 줄이지 않는다. 넓은 표·긴 코드는 `.tw`·`pre.code`가 가로 스크롤로 처리한다
- 시크릿·토큰·고객 개인정보는 넣지 않는다 (예시 값은 `●●●●●●` 또는 플레이스홀더)

## 1. report와 slidedeck

| | report (이 스킬) | slidedeck |
|---|---|---|
| 읽는 방식 | 혼자 스크롤하며 읽고, 나중에 다시 찾아본다 | 화면 공유·발표로 함께 본다 |
| 예 | 인수인계, 시스템 설명, 조사·분석 결과, 장애 회고, 런북, 설계 결정 기록 | 개념 교육, 팀 공유 발표 |
| 밀도 | 높음 — 표·코드·근거 링크를 한 페이지에 | 슬라이드당 한 아이디어 |
| 타이포 | 읽기 기준 (본문 15.5px, 본문 폭 820px) | 빔프로젝터 기준 (본문 17px 이상) |

애매하면: 독자가 나중에 다시 찾아볼 문서면 report, 한자리에서 함께 볼 자료면 slidedeck.

## 2. 문체와 근거 — 이 리포트의 품질 기준

- **평서문 `~다`체, 짧은 문장.** 수식어·감탄·홍보 어조를 쓰지 않는다. "~할 수 있습니다" 대신 "~한다"
- 한 문장에 사실 하나. 무엇이 무엇을 하는지 주어와 동작을 분명히 쓴다
- 식별자(저장소·경로·테이블·잡·명령·환경 변수·설정 키)는 전부 `<code>`
- **근거를 남긴다** — 독자가 문서를 믿을지 스스로 판단할 수 있어야 한다
  - 문서 머리 `.meta`에 기준 시점: 저장소·브랜치·커밋 7자리, 확인한 날짜
  - 섹션 끝 `p.src`에 근거 파일 링크. 브랜치가 아니라 **커밋 SHA로 고정한 permalink**(`…/blob/<sha>/<path>`)를 쓴다 — 시간이 지나도 링크가 가리키는 내용이 변하지 않게
  - 코드·문서로 확인하지 못한 내용은 단정하지 않고 `.callout`(「확인 필요」)으로 분리한다 — 무엇이 불확실하고 어떻게 확인할 수 있는지
- 같은 속성을 가진 항목이 3개 이상이면 산문 대신 표
- 부작용이 있는 명령은 `.callout.warn`을 먼저 두고, 예시 명령은 안전한 형태(`--dry-run`, 읽기 전용)를 기본으로 쓴다
- 링크 텍스트는 "여기" 대신 대상의 이름 (`<code>sources.yaml</code>`, 「나머지 시스템 인수인계」)

## 3. 테마 팔레트

배경·본문·코드·표·주의(amber) 색은 불변. 리포트마다 accent **라이트 한 쌍 + 다크 한 쌍**만 교체한다.
accent는 링크, 목차 현재 위치, 탭 밑줄, 기본 콜아웃에 쓰인다.

| accent | `--accent-l` | `--accent-soft-l` | `--accent-d` | `--accent-soft-d` |
|---|---|---|---|---|
| teal (기본) | `#0B6E8A` | `#E3F1F5` | `#5CC3DF` | `#16303A` |
| blue | `#2F5FD0` | `#E6EDFB` | `#8AB0FF` | `#1A2640` |
| violet | `#6A4BC4` | `#EEE9FA` | `#B9A4FF` | `#251E3D` |
| rose | `#B23A6F` | `#FAE6EF` | `#F293BD` | `#3A1C2A` |

같은 시리즈(예: 인수인계 묶음)는 accent를 통일하고, 다른 주제는 다른 accent로 구분한다.

## 4. 문서 구성

작성 순서:
1. 근거(코드·문서·대화)를 먼저 읽고 기준 커밋과 확인 날짜를 기록한다
2. `templates/report.html`을 복사해 머리와 개요부터 채운다
3. 예시 섹션 중 쓰지 않는 컴포넌트는 **지운다** — `{{…}}` 플레이스홀더나 빈 섹션을 남기지 않는다

서사 순서:

1. **헤더** `header.top` — `.brand`(문서 시리즈 — "팀 인수인계", "장애 회고") + `.ver`(범위 — 서비스·영역). 필요할 때만 `.switch`(§6)
2. **머리** — `h1`(대상의 이름) + `.lede`(이 문서가 무엇을 설명하는가 한두 문장) + `.meta`(기준 시점)
3. **개요** `#overview` — 전체 지도. 3~5문장 + 단계·구성요소 표 + (선택) 흐름도 한 장. 처음 읽는 사람이 여기까지만 읽어도 전체 그림을 잡게 한다
4. **각론** — 단계·구성요소마다 섹션 하나. 순서가 있으면 h2에 `①②③`. 각 섹션은 「한 문단 설명 → 표·목록으로 구체 → `p.src` 근거」 순서. 실행 방법·로컬 실행·백필 같은 하위 주제는 `h3[id]`로 나눈다
5. **운영 정보** — 환경별 연결(행 = 항목, 열 = dev/stage/prod 표), 권한·설정이 어디서 오는지
6. **참조** (선택) — 기준 저장소·브랜치 표
7. **이후 검토 사항** `#next` — "확정된 작업 목록이 아니다"를 밝히고 `<strong>주제</strong>: 현재 상태와 결정할 것` 목록

분량 가이드: 섹션 5~10개. 섹션 하나가 화면 서너 개를 넘으면 h3로 나누거나 섹션을 쪼갠다.

### 컴포넌트 사용 규칙

| 상황 | 컴포넌트 |
|---|---|
| 문서 머리 | `header.top` > `.brand` + `.ver` |
| 제목·요약·기준 | `h1` + `p.lede` + `p.meta` |
| 섹션 | `<section id="ascii-id" class="lv2"><h2>…</h2>` — id 필수 |
| 하위 주제 | `<h3 id="…">` — 딥링크가 필요 없으면 id 생략 가능 |
| 같은 속성의 나열·비교 | `.tw > table` (`thead` 필수, 표는 항상 `.tw`로 감싼다) |
| 동작·조건·규칙 나열 | `ul`/`ol` + `<li><strong>요지</strong>: 설명</li>` |
| 주의·부작용·실행 전 확인 | `.callout.warn` > `strong`(제목) + `div`(본문) |
| 보충·확인 필요 | `.callout` (같은 구조) |
| 코드·명령 | `pre.code > code`. 토큰 색은 선택: `.c` 주석 · `.k` 키워드/키 · `.s` 문자열 · `.n` 숫자 |
| 근거 | `p.src` — 섹션(또는 h3 블록) 끝, `소스: <a href="permalink"><code>파일</code></a> · …` |
| 흐름·순서 | `pre.mermaid` (§5) |
| 대안 중 하나만 보면 될 때 | `.tabs` (§6) |
| 문서 전체가 한 축으로 갈릴 때 | 헤더 `.switch` (§6) |

## 5. 다이어그램 (mermaid)

- 주로 두 가지: **흐름**(`flowchart`, 경계가 여럿이면 `subgraph`)과 **주고받는 순서**(`sequenceDiagram`)
- 개요에 전체 흐름도 한 장, 각론에는 순서가 핵심인 곳만. **섹션당 1개 이하**
- 원문은 `<pre class="mermaid">`에 그대로 적는다. HTML 안이므로 `<`는 `&lt;`, `&`는 `&amp;`로 쓴다
  (`-->`, `->>` 같은 화살표의 `>`는 그대로). 라벨 줄바꿈은 `["첫 줄&lt;br&gt;둘째 줄"]`
- 라벨은 짧게. 라벨 안에서는 HTML 서식이 되지 않으므로 식별자도 그냥 텍스트로 쓴다
- 렌더에 실패한 블록은 **원문(점선 상자)이 그대로 남는다** — 검증 때 점선 상자가 보이면 문법 오류다
- mermaid 코드를 "예시로 보여주고" 싶으면 `pre.code`에 넣는다 (`pre.mermaid`는 항상 그림으로 바뀐다)
- 다이어그램은 다크 모드에서도 흰 카드(neutral 테마)로 고정된다

## 6. 탭과 전역 스위치

- **`.tabs`**: 같은 자리에 대안 중 하나만 보여 주면 될 때 (macOS/Linux 설치, v1/v2 API, 변경 전/후).
  `.tab[data-p]`와 `.pane[data-p]`를 같은 키로 짝짓고, 첫 탭·첫 pane에 `on`. 탭 안에는 짧은 설명 + 코드나 표.
  코드·표만 든 pane은 가장자리까지 붙는다
- 탭으로 숨기면 안 되는 것: 독자가 **모두** 읽어야 하는 내용. 비교는 표로 한다
- **`.switch`**(헤더): 문서 전체가 한 축으로 갈릴 때 (Android/iOS SDK 가이드, 플랫폼별 런북).
  스위치 버튼의 `data-p`와 같은 키의 pane을 가진 모든 탭이 함께 바뀌고, 선택은 문서별로 기억된다.
  스위치에 없는 키의 탭은 독립적으로 동작한다. 템플릿의 주석 블록을 풀어 쓴다
- 인쇄 시 탭은 모두 펼쳐지고 탭 이름이 라벨로 붙는다

## 7. 동작 표준 (템플릿 JS에 이미 구현됨)

- 목차: `section.lv2[id] > h2`를 순서대로 읽어 자동 생성. h2와 `h3[id]` 제목은 자기 `#id`로 가는 링크가 된다 (제목을 눌러 섹션 링크 복사)
- 스크롤스파이: 화면 위쪽을 지난 마지막 섹션을 목차에서 강조. 페이지 끝에 닿으면 마지막 섹션
- 폭 900px 미만: 목차를 숨기고 한 단으로
- 다크 모드: OS 설정을 따른다. `<html data-theme="light">`/`"dark"`로 고정할 수 있다
- PDF: 브라우저 인쇄(⌘P) → "PDF로 저장". 헤더·목차는 빠지고, 다크 모드여도 라이트로 인쇄되며, 표·코드·콜아웃은 페이지 경계에서 쪼개지지 않는다
- 딥링크: `파일#section-id`로 그 섹션에서 열린다
- mermaid: `pre.mermaid`가 있을 때만 런타임을 불러와 성공한 블록만 `div.mmd`로 교체한다.
  이 로더가 문서에 있으면 publish-html은 자체 런타임을 덧붙이지 않으므로 로컬과 게시본이 같은 경로로 렌더된다

## 8. 작성 후 검증

1. 열어서 확인: `open <파일>` (또는 헤드리스 Chromium으로 스크린샷 — file: 프로토콜이 막혀 있으면 `python3 -m http.server`로 잠깐 서빙.
   mermaid는 네트워크로 불러오므로 스크린샷 도구에 대기 시간을 준다)
2. 기계 검사:
   - 플레이스홀더 잔여: `grep -n '{{' <파일>` 결과가 없어야 한다
   - id 중복: `grep -o ' id="[^"]*"' <파일> | sort | uniq -d` 결과가 없어야 한다
3. 눈으로 확인:
   - 목차에 모든 섹션이 순서대로 있는가 (빠진 섹션은 `section`의 id나 h2 누락)
   - mermaid가 모두 그림으로 바뀌었는가 (점선 상자 원문이 남았으면 문법 오류)
   - 브라우저 폭을 900px 미만으로 줄였을 때 표·코드가 본문 밖으로 넘치지 않는가
   - 탭·스위치를 쓰면 전환이 되는가, 다크 모드에서 읽히는가
4. 내용 확인: 모든 섹션에 근거(`p.src` 또는 `.meta` 기준)가 있는가 / 확인하지 못한 내용을 「확인 필요」 콜아웃으로 분리했는가 / 시크릿·개인정보가 없는가
5. 산출물 위치: 관련 프로젝트의 `docs/` 아래 (예: `docs/<주제>-report.html`). 프로젝트가 없으면 사용자에게 위치를 확인
6. 사내 공유가 필요하면 `publish-html` MCP로 게시 (VPN 내부 링크) — **사용자가 요청할 때만**.
   public 게시는 `list_tags`로 기존 태그를 먼저 고른다. 섹션 id가 ASCII여야 응답에 섹션별 링크가 나온다

## 9. 파일 구조

```
html/                        # 플러그인 — 호출은 /html:report (발표용은 같은 플러그인의 slidedeck)
└── skills/report/
    ├── SKILL.md             # 이 문서
```
